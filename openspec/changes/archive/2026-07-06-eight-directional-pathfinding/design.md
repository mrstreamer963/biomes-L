## Context

Текущий A* в `pathfinding.rs` использует 4 направления и Манхэттенскую эвристику. Пути получаются ступенчатыми: чтобы пройти из (0,0) в (3,3), нужно 6 шагов вместо 3 диагональных. Waypoints (центры тайлов) и lerp-движение между ними работают корректно, но траектория неестественная из-за зигзагов.

Переход на 8 направлений — минимальное изменение с максимальным эффектом: waypoints остаются центрами тайлов, lerp не меняется, но путь уже не зигзаг.

## Goals / Non-Goals

**Goals:**
- A* строит пути с диагональными шагами
- Эвристика Чебышев (cost = max(dx, dy) для октолий)
- Стоимость прямого шага = 1.0, диагонального = √2 ≈ 1.414
- Проверка блокировки диагонали смежными стенками (diagonally-adjacent passability)
- Типы счётчиков: u32 → f64

**Non-Goals:**
- Изменение системы waypoints (остаются центрами тайлов)
- Изменение movement_system (lerp уже поддерживает любые направления)
- Оптимизация производительности A* (кроме неизбежной при 8→ соседях)

## Decisions

### Decision: f64 для g_score/f_score вместо u32

**Why**: Стоимость диагонального шага √2 = 1.414... нецелая. Можно было бы умножать на 1000 и хранить в u32 (1414 вместо 1.414), но f64 проще и понятнее. Размер карты 50x50 → максимальная длина пути ~2500 шагов, даже с f64 проблем с производительностью не будет.

**Alternatives considered**: 
- `u32 * 1000` — экономит память, но добавляет лишнюю арифметику. Неоправданно для сетки 50x50.

### Decision: Diagonally-adjacent passability check

При диагональном шаге из (c, r) в (c+1, r+1) проверяем проходимость (c+1, r) И (c, r+1). Если любой непроходим — шаг отклоняется.

```
┌────┬────┐     Легенда:
│    │ ## │     ## = непроходимо
├────┼────┤     ╱  = заблокировано (проход через угол стенки)
│    │    │     →  = разрешено
└────┴────┘

(c,r) → (c+1,r+1): проверяем (c+1,r) и (c,r+1)
Если (c+1,r) непроходим → диагональ из (c,r) в (c+1,r+1) заблокирована
```

**Why**: Без этой проверки юнит может "прорезать угол" препятствия, проходя по диагонали между двумя непроходимыми тайлами, которые соприкасаются только углом.

**Alternatives considered**: 
- Разрешить любые диагонали — неестественное поведение, юнит проходит сквозь стыки стен.

### Decision: Chebyshev эвристика

```
h = max(|dx|, |dy|)
```

**Why**: Для октолий (8 направлений с равной стоимостью прямых и возможностью двигаться по диагонали) Чебышев — допустимая и монотонная эвристика. Даёт оптимальные пути.

**Alternatives considered**: 
- Euclidean (sqrt(dx² + dy²)) — допустима, но медленнее считать и менее точно направляет поиск.
- Octile (dx + dy + (√2-2)*min(dx, dy)) — точнее Чебышева, но сложнее. Для сетки 50x50 выигрыш минимален.

### Decision: Умножение стоимости на 2 для обхода дробей (НЕ используем)

Была идея умножить все стоимости на 2: прямой = 2, диагональ = 3 (вместо √2 ≈ 1.414). Это дало бы целые числа. Но это потеря точности: 3/2 = 1.5 ≠ √2 ≈ 1.414. На коротких путях разница незаметна, на длинных может давать неоптимальные пути. Используем f64.

## Risks / Trade-offs

- **Производительность A***: 8 направлений вместо 4 = до 2x больше соседей для проверки. Для карты 50x50 это несущественно (2500 клеток максимум).
- **Валидация старых тестов**: Все тесты pathfinding, которые проверяют конкретную длину пути, сломаются — пути станут короче. Нужно обновить ожидаемые значения.
- **Diagonally-adjacent check**: Добавляет 2 extra lookups на диагональный шаг. Незначительно.
